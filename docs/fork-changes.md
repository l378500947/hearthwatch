## 分支结构（**只有两个**）

```
main (上游基准)
 ├── localization .... 面板汉化（纯前端 panel/）
 └── features ........ 所有服务端插件改动（plugin/ + tools/）
```

### ⭐ 为什么按这个维度分

**按"改动性质"分，不按"每次需求"分。**

| 好处 | 说明 |
|---|---|
| **零文件重叠** | `localization` 只碰 `panel/`，`features` 只碰 `plugin/`+`tools/` ⇒ **永不冲突** |
| **可独立 rebase** | 上游改动不会同时撞两边，处理一边不影响另一边 |
| **可独立提 PR** | 面板汉化是干净的通用功能贡献，可单独提 |
| **好记** | 两个分支看一眼就知道该往哪加东西 |

⚠️ **之前是 5 个按需求分的分支（链式堆叠），已合并成这两个并删除**。
链条式堆叠的坏处：rebase 要从最底层逐层重建，且容易忘记哪层含哪层。

## 怎么用这些分支

**拿全部改动**：
```bash
git checkout features
```

**只要面板汉化**：
```bash
git checkout localization
```

**两个都要**（比如要一起部署）：按顺序 merge 或 cherry-pick 到本地集成分支。
⚠️ **零文件重叠 ⇒ merge 不会冲突**，顺序无所谓。

**编译插件**：
```bash
./tools/build-patched-arena.sh        # 在 features 分支
```
⚠️ 构建产物（`.dll`）**不入库**；`refs/`（游戏原版 DLL，有版权）同样不入库。

## 维护约定

- **按性质分两类，不按需求开新分支** —— 汉化进 `localization`，
  插件功能进 `features`。⚠️ 别再按"每次需求"开分支了。
- **每个分支都有自己的 `FORK.md`** —— 记录：改了什么 / 为什么 / 怎么验证 / 怎么回滚
- ⚠️ **`README.md` 不要动** —— 它是上游的文件，改它会增加 rebase 冲突。
  本 fork 的记录一律放 `FORK.md`
- **构建产物与游戏原版 DLL 不入库** —— 见 `.gitignore`
- **绑定的判据**：新改动若**同时涉及前端与插件**，才考虑临时开第三个分支；
  否则一律归入现有的两个。
